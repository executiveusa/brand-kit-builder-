# ZTE-20260812-0004 — Phase 3 Cloud Operating Layer

## Objective
Add a tenant-safe Supabase operational layer and wire the POLISH web app to a typed persistence boundary without making Supabase the canonical owner of brand intelligence.

## Classification
Brownfield / MEDIUM risk.

## Current truth
- Phase 0 architecture, Phase 1 ICM organization, and Phase 2 human design office are merged to `main`.
- `botanic-creations` is the only connected Supabase project.
- It is shared by multiple Pauli systems; existing public tables use RLS.
- No `brand_studio_*` tables currently exist.
- No Supabase development branches currently exist.
- Production schema mutation is NOT approved by the current instruction.

- Supabase: auth, tenancy, memberships, sessions, work-order/job indexes, approvals, sync metadata, artifact metadata, activity events.
- Git: source and migrations.
- Secrets: deployment secret stores only.

## Security laws
1. Every tenant-owned table has RLS.
2. Tenant selection is derived from membership, not client-supplied trust.
3. Write permission is role-gated.
4. Approval and activity rows are append-only.
5. No service-role key is exposed to the browser.
6. Client uses publishable/anon capability only.
7. No editable copy of the canonical brand manifest is stored in Supabase.
8. Artifact rows store metadata/hash/location, never become the only portable copy.

## Validation criteria
PASS only when:
- migration SQL is reviewable and reversible;
- all new tables have RLS;
- cross-tenant read/write tests are present;
- append-only audit/approval behavior is tested;
- TypeScript/build/lint/Playwright pass;
- UI never claims persistence when cloud configuration is absent;
- no production migration or secret mutation occurs without explicit approval.

## Rollback
Before production application, record the exact migration version and create a rollback SQL package that drops only `brand_studio_*` policies/triggers/functions/tables in reverse dependency order. Application rollback is PR revert. No existing shared tables are altered.

## Risk
MEDIUM. The schema is isolated by prefix, but the target Supabase project is shared infrastructure. Production DDL therefore remains gated.
